Paint stickers on the net to set a position: pick a color, then click or drag. Right-click a sticker to pick up its color. Whenever the painted position is valid, it becomes the position.

    Solves the position with twsearch, natively through the twsearch bridge if it is running on this computer, otherwise in the browser.

      Solving with twsearch
      
          
      
          
      
            
      The solver hands twsearch the current position to solve.  This can
              be the position at the end of an algorithm from the algorithm
              box, or the position set in the Colors tab, or the position set
              by the Scramble button.  The search for an optimal solution will
              proceed; if it completes, the solution(s) will appear as
              button(s) you can click to apply that solution.  Some solutions to
              certain positions on certain puzzles may appear instantly; others
              may take a very long time, so there is a Cancel button.
      

            
      Move set
      
            
      Comma separated move names, as this puzzle names them:
              U,R,F, or u,r,f for a different set of
              moves.  No spaces.  Leave it blank for the puzzle's own moves.  The
              move set decides the puzzle twsearch is given, so it also decides
              which positions count as solvable, in the Colors tab as well.  It is
              kept per puzzle while the page is open, and is not part of the URL.
              The move set also limits the Scramble button: it scrambles with
              those moves only, so the solver can always solve the result.
      

            
      Options
      
            
      Anything below can go in the Options field, separated by spaces.
              --checkbeforesolve is always added, so an unsolvable
              position is refused instead of searched forever.  The most useful
              options in general are -c, -M, -q, --distinguishall, and the various
              options starting with --no or --omit.
      
            
      
            
      twsearch's other commands (-g, --schreiersims
              and the rest) are not available here; they do not solve a position, and
              the browser build leaves most of them out.
      

            
      Searching in a tab you are not looking at
      
            
      Browsers give a hidden tab a fraction of the processor, to save
              battery.  Measured on one laptop, a search in the browser runs about
              five times slower once its tab is behind another one, and it
              speeds back up the moment the tab is visible again.  That is not
              something this page is doing: a loop that never pauses is slowed just
              as much, because it is the page's priority that changes, not its
              behavior.  On a laptop with efficiency cores, the browser is moving
              the work onto them.
      
            
      Keeping the window visible costs nothing, and it does not have
              to be the window you are typing in: an unfocused window that is still
              on screen runs at full speed.  Putting this window beside a terminal
              is enough.
      
            
      Disable browser throttling is for when the tab really must be
              hidden.  While a search is running it plays a tone far too quiet to
              hear, which makes the browser treat this as a tab that is doing
              something and leave its speed alone.  It is a trick on the browser's
              battery saving, so it is off unless you turn it on, and it is worth
              it only while you are plugged in.  The tone stops when the search
              does, so the speaker mark on the tab is also a sign that a search is
              still running.
      
            
      So is the spiral beside the title, which turns while twsearch is
              working, whichever tab you are looking at.
      
            
      None of this applies to twsearch running natively, which is
              not a browser tab at all.
      

              
      The server
      
              
      By default the twsearch code is run in the browser through WebAssembly.
              This is not as fast as a native build, and it does not use threads
              and can only use up to 4GB of RAM.  It also cannot write pruning
              tables to disk.  For more speed and deeper searches, you can run a
              native server (see below) or use the Export... button to
              download a file to run locally from the command line.  This file
              contains both the puzzle definition and the puzzle state to solve.
      

            
      Running twsearch natively
      
            
      For bigger searches (such as a random 3x3x3 position), run twsearch on your
              own machine.  The solver finds it automatically and shows
              native (twsearch bridge).  Nothing leaves your machine.

      Leave it running, and then open http://127.0.0.1:2023/: twsearch
              answers with this page, fetched from this site and kept up to date, and
              searches for it.  Browsers no longer let a page on the web reach a
              program on your own machine, so a page from twsearch itself is the way
              to have one.
      
            
      The first search on a puzzle builds a pruning table (minutes for a
              3x3x3); later ones take seconds.  -M 16384 gives it 16GB.
              Stop it with Ctrl-C.  --port puts it somewhere other than
              2023, and the page it serves follows it there.
      
            
      On Linux, or to build it yourself: git clone
              https://github.com/rokicki/twsearch, then make build
              (needs a C++ compiler).
      
            
      twsearch is at github.com/rokicki/twsearch: the source, the
              releases, what the options do, and the protocol this page uses to
              talk to it (docs/bridgeprotocol.md).
      
            
      The -M option is important, as is the --writeprunetables option; you can
              give both of these either to a command line twsearch to run an exported puzzle
              or to the server twsearch.  The memory size provided to the -M option should be
              less than the physical memory of your machine (in megabytes) to allow memory
              for the operating system or other applications; choosing half the physical memory
              is a good value to start with.  If you write pruning tables, note that every
              different move set or puzzle writes a distinct pruning table and these can fill
              up your disk if you don't have much space.  The twsearch log on the Solver pane
              will tell you precisely where these files are stored if you should need to clean
              them up.
